## Context

Сейчас в репозитории нет приложения и серверного кода; см. [proposal.md](proposal.md). Целевые устройства — Android и macOS. Сервер на этом этапе запускается локально; публичный деплой и функции конкретных активностей будут отдельными изменениями. Требования к поведению перечислены в `specs/` этого изменения.

## Goals / Non-Goals

**Goals:**

- Проверить путь данных от установленного клиента через API и постоянное хранилище до второго клиента.
- Сформировать независимые границы для будущих активностей без универсальной таблицы с полями всех активностей.
- Сохранить возможность добавить локальные изменения и отложенную отправку позднее, не меняя публичный контракт профиля.

**Non-Goals:**

- Фоновая синхронизация, автономное редактирование, разрешение конфликтов содержимого активностей и отправка уведомлений.
- Публикация API, настройка домена, магазины приложений и производственная подпись сборок.
- Хранение обложек и иных вложений до появления модуля, которому они нужны.

## Decisions

### 1. Один Flutter-клиент с целями Android и macOS

Клиент располагается в `apps/client`. Общие экраны, состояние входа и навигация реализуются один раз; расположение навигации адаптируется под телефон и широкое окно. Flutter [поддерживает обе целевые платформы](https://docs.flutter.dev/reference/supported-platforms) и описывает [архитектуру локального и удалённого источников](https://docs.flutter.dev/app-architecture/design-patterns/offline-first). Альтернатива — Tauri 2 с веб-интерфейсом, который также [собирается для Android и macOS](https://v2.tauri.app/); для нового приложения без существующего веб-кода Flutter даёт прямой путь к общему мобильному и десктопному клиенту.

Клиент имеет слои UI, доменных моделей, репозиториев и транспорта. Адрес API задаётся конфигурацией сборки/запуска. Токен сессии хранится в защищённом хранилище платформы; обычные настройки и последняя подтверждённая версия профиля могут храниться локально. У клиента есть точка подключения локальной БД для будущих модулей; реализация очереди автономных изменений откладывается.

### 2. Модульный сервер с версионированным HTTP API

Сервер располагается в `apps/api`: TypeScript, Fastify, PostgreSQL и миграции схемы. Fastify предоставляет [модули и изоляцию плагинов](https://fastify.dev/docs/latest/Reference/Plugins/) и [проверку запросов по схемам](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/). На сервере будут отдельные области `auth`, `profile` и реестр модулей активностей. API получает префикс `/v1`; контракт запросов и ответов документируется машинно читаемой схемой OpenAPI, по которой сверяется клиент. Альтернативы — SQLite на сервере или управляемый бэкенд: SQLite уменьшил бы локальные зависимости, а управляемый сервис ускорил бы старт, но PostgreSQL оставляет явные ограничения данных и миграции в собственном коде независимо от будущего хостинга.

Локальный запуск использует PostgreSQL в контейнере и API на машине разработчика. Для Android-эмулятора адрес API настраивается отдельно; физический телефон может использовать адрес Mac в той же локальной сети. Незашифрованное локальное соединение допускается только в debug-конфигурации; сборки вне локальной разработки требуют HTTPS.

### 3. Заранее созданный владелец и отдельная сессия устройства

Публичной регистрации нет. Локальная команда инициализации создаёт единственного владельца и запрашивает пароль через интерактивный ввод, без пароля по умолчанию или секрета в репозитории. Пароль хранится как Argon2id-хеш по [рекомендациям OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). В БД есть записи сессий; клиент получает случайный непрозрачный токен, а сервер хранит только его хеш, срок действия и владельца. Выход удаляет запись текущей сессии. Такой подход даёт точечный выход без списка отозванных JWT; альтернатива — подписанные токены с отдельной схемой отзыва. Требования к непредсказуемости и серверному завершению сессий согласуются с [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

### 4. Профиль как сквозной сценарий синхронизации

Профиль содержит `display_name` и монотонную `revision`. `GET /v1/profile` возвращает подтверждённое значение и ревизию. `PUT /v1/profile` передаёт новое имя и прочитанную ревизию; сервер проверяет непустое имя и атомарно обновляет запись только при совпадении ревизии. При устаревшей ревизии ответ `409` возвращает актуальный профиль. Клиент показывает конфликт и предлагает загрузить актуальное значение для повторного изменения. Альтернатива — правило «последняя запись побеждает», которое может незаметно потерять изменение с другого устройства.

После успешного ответа клиент хранит подтверждённую копию и показывает состояние «синхронизировано». При открытии профиля и ручном обновлении он делает `GET`; при ошибке сети показывает ошибку и не подтверждает сохранение. Автономное редактирование в этой итерации не включается, однако ревизии и разделение локального/удалённого источников позволяют добавить очередь изменений позднее.

### 5. Модули активностей подключаются при сборке

В клиенте модуль объявляет стабильный ID, название, начальный экран и необязательные точки входа в настройки. Главная навигация строится из зарегистрированных модулей; при пустом реестре показывается пустое состояние. На сервере модуль подключает собственные маршруты под `/v1/activities/<id>` и собственные миграции/таблицы. Общие слои предоставляют идентификацию владельца, транспорт и базовую инфраструктуру; содержимое сессий, метрики и настройки определяет сам модуль. Для проверки контракта используется тестовый модуль в автоматизированной проверке, без выпуска фиктивной активности пользователю. Альтернатива — единая универсальная таблица записей; она вынудила бы чтение и программирование делить не относящиеся к ним поля и правила.

## Risks / Trade-offs

- [Нет публичного сервера] → Сквозную проверку выполняем в одной локальной сети или через эмулятор; удалённый доступ остаётся задачей этапа деплоя.
- [Профиль не редактируется без сети] → Клиент явно сообщает об ошибке и сохраняет только последнюю подтверждённую копию; очередь изменений добавляется отдельным изменением.
- [Две технологические экосистемы: Dart и TypeScript] → Контракт API фиксируется OpenAPI и проверяется интеграционными тестами, чтобы модели не расходились.
- [Секреты локальной разработки могут утечь в репозиторий] → Шаблон конфигурации содержит только имена переменных; реальные значения и локальные файлы исключаются из Git.
- [PostgreSQL усложняет локальный запуск] → Команды запуска и миграций оформляются в README, БД поднимается одним локальным сценарием.

## Migration Plan

Существующих данных и пользователей нет. Применение начинается с создания структуры проекта и первой миграции, затем инициализируется владелец, запускаются API и клиенты, выполняется сквозная проверка. Откат до первого использования состоит в остановке локальных процессов и удалении созданной локальной БД по отдельной явной команде; пользовательские данные автоматически не удаляются. Публичный деплой и производственная миграция откладываются.
